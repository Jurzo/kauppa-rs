### P3 checklist (owner, manual: keyboard and screen reader)

At a phone width (e.g. 390 px in DevTools device mode, and Android TalkBack on a real phone; Firefox and one of Chrome/Safari):

1. Tab to "Menu": it is announced as a button named "Menu", collapsed. Browsers expose a `popovertarget` button's expanded state themselves (no `aria-expanded` in the markup, which couldn't be kept in sync without JavaScript).
2. Enter/Space opens the panel; it is announced as expanded, and focus lands on the "Close menu" button inside the panel (`autofocus` on that button; the popover focusing steps honour it). Tab moves through Lists, Recipes, Favorites, Categories, Sign out (or Sign in). Note: a popover is not modal, so Tab can leave the panel to the page behind it; that's the native behaviour, not a focus trap.
3. Escape closes it and focus returns to "Menu" (browsers return focus to the previously focused element when a popover that contains focus is hidden). Same for "Close menu" and for tapping/clicking the backdrop.
4. Choosing an entry navigates (boosted); the new page shows the panel closed.
5. On a section page (e.g. `/lists`, a list, a recipe) the screen reader announces the current entry as "current page".
6. Sign out from the panel signs out (POST; the cross-site check still applies).

## Decisions and constraints

- 2026-11-09, owner: brief accepted. Pattern: native **`popover`** panel opened by a menu button (`popovertarget`) on phones; Escape and outside tap (light dismiss) close it; no JavaScript. On wide screens the links stay **inline** in the top bar and no menu button shows. Breakpoint is the agent's choice (`may_decide`). Choosing an entry navigates (hx-boost swaps `<body>`), which leaves the panel closed. Sign out stays a POST form (MB-0018) inside the panel.
- `page_nav` layout parameter (RR-0006 constraint 1: `page_` prefix), optional; passed by `lists/{index,show,shop,sharing}`, `recipes/{index,show}`, `products/index` (favorites), `categories/index`. The P1 test pins which pages pass which value.
- Breakpoint (agent, may_decide): **40rem (640 px)**. Below it, the panel; at and above it, inline. Brand + four links + Sign out need roughly 450 px, so 640 px leaves room at 16 px text and larger; phones in portrait (320–430 px) always get the panel.
- Desktop inline over the UA's popover rules: `.site-nav` resets the UA popover box (`position: static; inset: auto; margin: 0; padding: 0; border: 0; width/height: auto; overflow: visible; background: none; color: inherit`) and sets `display: flex`. Author-origin declarations beat the UA stylesheet regardless of specificity, so this overrides `[popover]:not(:popover-open) { display: none }` in Chrome, Firefox and Safari alike (the UA rule isn't `!important`). Only inside `@supports selector(:popover-open)` and `@media (max-width: 39.9375rem)` does `.site-nav:not(:popover-open) { display: none }` hide it again and the panel styles apply. Browsers without popover support (Safari < 17, Firefox < 125, Chrome < 114) get the inline links at every width, with both buttons hidden: no dead menu button.
- Focus: `autofocus` on the close button, so opening moves focus into the panel. It doesn't steal focus on load or after boosted swaps (htmx focuses the first `[autofocus]` in swapped content): the button is `display: none` whenever the panel is closed or inline, so `focus()` is a no-op. No template uses `autofocus` today; htmx 2.0.3 looks for `[autofocus]` per swapped top-level node (`<header>`, then `<main>`), so a page's own `autofocus` in `<main>` would still get focus after a boosted swap.
- Accessible names: menu button "Menu" (icon `aria-hidden`), close button `aria-label="Close menu"`, `<nav aria-label="Main">`.
- Animation: slide-in via `transform` + `@starting-style` + `transition-behavior: allow-discrete` on `display`/`overlay`, only under `prefers-reduced-motion: no-preference`; browsers without `@starting-style` just show the panel.
