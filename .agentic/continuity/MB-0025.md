## Decisions and constraints

Made under the brief's `may_decide`:

- **Options, not raw pragmas.** Settings come from typed `SqliteConnectOptions` methods (`journal_mode(Wal)`, `synchronous(Normal)`, `busy_timeout`, `foreign_keys`). sqlx applies them on every new connection, and the compiler checks them.
- **Busy timeout 10 s** (`BUSY_TIMEOUT`). Writes take milliseconds and start with `BEGIN IMMEDIATE`, so the busy handler always applies; even all 7 other connections writing ahead clear far inside 10 s. sqlx's default is 5 s, the brief's floor; 10 s leaves headroom for SQLite's non-FIFO busy-handler backoff (a waiter can lose several rounds) and a slow disk at checkpoint. It stays below the pool's 30 s acquire timeout, so a stuck lock surfaces as an error instead of a hung request.
- **Pool size stays 8** (`MAX_CONNECTIONS`, now a named const used by P1). In WAL, extra connections only add concurrent readers; writers are still serialized. persistence.md says not to raise it without benchmarking, and nothing here needs more.
- **Durability: `synchronous=NORMAL` kept; no escalation.** In WAL mode NORMAL can't corrupt the database, and an application crash or kill loses nothing. Only an OS crash or power loss can roll back commits made since the WAL was last synced (at checkpoint). On a VM host that's rare, and the data is shopping lists and recipes, so losing a few seconds of edits after a host power failure is an accepted trade-off. The brief's goal names NORMAL. The owner can still overrule this: switching to `FULL` is a one-line change and P1's assertion would change with it.
- Tests use temp-file databases under `std::env::temp_dir()` with a uuid name, removed on drop (with `-wal`/`-shm`/`-journal`). `tempfile` is only a transitive dependency; adding it as a dev-dependency would be a dependency change, so it wasn't added.
- P3's writer takes `BEGIN EXCLUSIVE`, the strongest write lock, so the test tells WAL from rollback-journal mode (a plain `RESERVED` lock doesn't block readers in either mode).
- No `.env` setting added (that would be an escalation); no dependency or sqlx feature change.
