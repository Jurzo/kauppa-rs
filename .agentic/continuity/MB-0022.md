## Dead ends and rejected approaches

- Testing the Caddyfile with a downloaded Caddy binary: refused by the harness (running external code). Validation happens on the first `smoke_compose.sh` run.
- Rendering cloud-init with `terraform apply` on a scratch config: refused (no apply of any kind). `terraform plan` on a scratch config rendered it instead.
- `user_data` assertions in `terraform test`: the provider stores `user_data` hashed, so assertions on it would pass vacuously; the static check in `check_terraform.sh` reads the template instead.
- Reading spoofed `X-Forwarded-For` or query strings from the app's own logs: release builds log JSON events, and `TracingLogger` spans don't appear as lines at INFO, so such a check passes vacuously. `smoke_compose.sh` swaps in a temporary echo upstream (the pinned Caddy image) under the alias `kauppa` instead, which also tests Host passthrough.

## Decisions and constraints

- Owner decision (2026-11-08): DigitalOcean VPS, Docker with Caddy, Terraform. RR-0014 answers Q1–Q7 and is the contract.
- `may_decide` choices made here:
  - Layout: `deploy/{Dockerfile,docker-entrypoint.sh,healthcheck.sh,compose.yaml,Caddyfile,.env.example,README.md}`, `deploy/backup/`, `deploy/terraform/`; scripts under `scripts/deploy/` with a shared `lib.sh`.
  - Base images pinned by tag and digest (rust 1.99.1 slim trixie, debian trixie 2026-11-04 slim, caddy 2.11.9 alpine, alpine 3.24.4); backup packages pinned to minor versions from that Alpine branch.
  - Health check: the existing `GET /healthz`, via bash `/dev/tcp` (no curl in the runtime image).
  - Container hardening: app read-only root, `cap_drop: ALL`, `no-new-privileges`, internal network with no egress; Caddy `cap_drop: ALL` + `NET_BIND_SERVICE`; HTTP/3 off (the firewall opens TCP only).
  - The backup image is built on the droplet by Compose from `deploy/backup/` (pinned Alpine, packages only, no compiling). RR-0014 Q4 asks for "a small pinned image" without saying how it gets there; Q1's concern (compiling on a 1 GB host) doesn't apply. If the owner prefers, the CI workflow can push it as a second GHCR package later.
  - Restore: `kauppa-backup restore --app-stopped <object>` moves the old `kauppa.db` set (with `-wal`, `-shm`, `-journal`) into `db/pre-restore-<ts>/` instead of deleting it; the explicit flag is the guard against restoring under a running app.
  - Retention "12 months" is 365 days in the lifecycle rule.
  - IPv6 off by default (`enable_ipv6`): the reserved IP is IPv4 only and a droplet's IPv6 changes on replacement, so RR-0014 Q5's "AAAA if the droplet has IPv6" doesn't arise by default.
  - SSH: root with key only (`PermitRootLogin prohibit-password`, no passwords); the cloud firewall limits 22 to `ssh_allowed_cidrs`, whose validation rejects `/0` and any prefix shorter than `/8`.
  - Caddy certificates live in a named Docker volume on the droplet's disk (re-issued if the droplet is replaced), not on the data volume.
  - The Terraform state bucket name is passed with `-backend-config="bucket=…"` (a name, not a credential; RR-0014 forbids `-backend-config` for credentials).
- Not done here, by RR-0014: no Rust, `Cargo.toml` or `migrations/` change; no DNS resource; no deploy job or credential in CI; no `terraform apply`/`destroy`.
- Follow-up from MB-0023 (RR-0012 constraint 9): invitation links carry their token in the query (`/auth/register?invite=…`). The app logs paths only; the Caddyfile must leave access logs off, or drop the query with a `log … format filter` rule. First admin on the droplet: `docker compose exec <app> kauppa-web admin invite`, register with the printed link, then `… admin grant <email>` (RR-0012 sub-answer 3). Rolling the binary back past 0008 needs the pre-deploy backup or a manual delete of `_sqlx_migrations` version 8 (constraint 8).
