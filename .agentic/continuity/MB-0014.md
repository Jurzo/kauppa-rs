## Decisions and constraints

- Owner (2026-11-06): brief accepted as written.
- `may_decide`:
  - Method names/shapes: `list_hidden_with_usage(owner) -> Vec<HiddenProductGroup>` (domain types `HiddenProductGroup`, `ProductUsage { product, recipe_count }`); `make_favorite(owner, id) -> Product`, a no-op for an existing favorite. Usage counts distinct recipes of the owner (`COUNT(DISTINCT r.id)` joined on `r.owner_id`, RR-0001 constraint 9).
  - Section: heading "From recipes", always expanded, below the favorites, rendered only when the user has such products; category groups are `<h3>`. An uncategorized product shows "No category: set one under Edit" and no "Make favorite" button (the server refuses it anyway).
  - Ordering within a category: by name, ignoring case.
- Implementation decision (within P5's "keep their name"): `ProductRepo::delete` runs in a transaction that first copies the product's current name into its ingredients' `text` (owner's recipes only), so a renamed product's ingredients keep the new name after it is deleted. Before, they fell back to the name saved when the ingredient was added.
- Only one route added (`POST /favorites/{id}/favorite`), as the brief allows; no schema, dependency, or lint change; no escalation trigger fired.
